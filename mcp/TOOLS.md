# DataArcus MCP: the tool reference

Every tool, every option and what each answers, in detail. To install DataArcus and start, read [README.md](README.md)
first; how the parts fit together: [ARCHITECTURE.md](../ARCHITECTURE.md). (Moved here from the README by G1, 0.3.1, text unchanged.)

DataArcus works next to Microsoft's Power BI Authoring MCP server (model edits, DAX queries) and the Power BI Desktop
bridge (reload, screenshots).

## `read_model`

| Tool | What it does |
|---|---|
| `read_model` | Tables, visible columns with types, measures with formats, date tables. Reads a project folder (TMDL or model.bim), a model.bim or a .pbit. `existingReports`: the names of the reports already beside the model (a new report never takes one). Changes nothing. A large model (a full answer over 40,000 characters) gets a summary first: counts, the date tables, the areas (measure display folders), the tables with measures and the other tables' names. `tables: [...]` returns named tables in full, on any model. A TMDL file it can't read fully is named, not skipped silently (0.3.1): `unreadable` comes first, with the file and why; plan_layout, create_report, add_gulf_calendar and create_arabic_twin then refuse to plan. A visible measure with a KPI in the model is listed in `kpis` with its target: a measure, or "an expression" (never its text). Optional `lang` (`ar` or `en`, 0.3.2): the language the user writes in, for an answer about which model is meant (several models in one folder); without it the folder and model names decide. **0.3.3, Impact check before an edit:** `reach` (`"[Measure]"`, `"Table[Column]"`, `"Table"`, a name with spaces quoted as DAX does: `'Sales Data'[Amount]`; not with `tables`) answers, instead of the model list, the pages and visuals of every report saved beside the model that it reaches, by tier (question, display, order), through the measures that call it and the relationships a filter can travel: per report its visuals counted, by page; at most 60 visuals listed in all, every one counted; a name the model lacks is answered `found: false`. A measure written with its table (`Sales[Total Sales]`) is read as the measure. A report elsewhere that uses the model is not seen. |

## `suggest_fields`

| Tool | What it does |
|---|---|
| `suggest_fields` | Which measures and columns go in each KPI card, chart, table and slicer (same rules as the theme generator). Optional `focus` (a word the user said, such as "logistics") or `tables`: the picks then come from that part of the model (the matching tables with measures, the tables related to them, the date tables). A large model needs one: without it nothing is picked and the areas are listed. |

`columnStats` (0.3.1, FX4): counts only, `{ rows: { "Table": n }, distinct: { "Table[Column]": n } }` (whole numbers; COLUMNSTATISTICS()'s Cardinality, never its Min or Max). With them no category is a column of one value or of mostly unique values (90% of its rows, over 100 rows; or over 5,000 values), and a month name gives way to a year-month axis (or the date) when the years are more than one; without them `countsNote` says only the name rules applied. Always: no coordinate or invoice column as a category, net before gross, and `why` says each rule that acted.

## `check_model_health`

| Tool | What it does |
|---|---|
| `check_model_health` | The Model Health Check (the same engine as the website's): score and every finding with its objects and its rule's source (a Microsoft Learn page, a Microsoft Best Practice Analyzer rule, or a DataArcus rule with its reason). Only the reports whose `definition.pbir` points at the checked model are read (`reports.counted`); another project's reports in the same folder, and reports connected to a published model, are named with why under `reports.notCounted` and never read. Reads a project folder (TMDL or model.bim), a model.bim or a .pbit. On a TMDL project, checks that need the type of a DAX table's column are listed as skipped (the files don't have it), with how to get them. Optional `columnTypes` (`{ "Table[Column]": type }`, read from the same model open in Desktop) fills those types, so every check runs; types the files give are never replaced, and names or types that can't be used are listed back. Fix scripts are written only with an approved `planId` (without one the findings come back, the script files are named and a `planId` is proposed). Returns `fixes` for three findings (`MONTH_SORT`, `NO_FORMAT`, `PCT_FORMAT`): a TMDL script to paste into Desktop's TMDL view, the suggested format and its reason per measure, and steps by hand for what a script can't change safely; nothing is ever applied. Optional `weekStart` (`sunday` by default, `monday`, `saturday`) for a weekday number the sort script adds. For a Gulf model: optional `country` (`uae`, `ksa`, `qat`, `kwt`, `bhr`, `omn`) adds a `gulfCalendar` section, **not part of the score**: whether the calendar has Hijri, Ramadan and Eid columns and the model has Ramadan and Eid measures; for a calendar made by the DataArcus Calendar Generator also its weekend against the country's official weekend, its Ramadan and Eid dates against the announced ones (the UAE and Saudi Arabia, whose announced dates match for 2018-2026; for Qatar, Kuwait, Bahrain and Oman a date that differs from Umm al-Qura is only a low note to check the official announcement, and for Oman a date on one of its own sourced announcements is not a difference), unmarked estimates and a range that ends before the next Ramadan. What the files can't say is listed under `cantTell`. Its fixes name the website tools and the settings to pick (no DAX), and `fixes.addGulfCalendar` gives the same settings as `add_gulf_calendar`'s inputs. Optional `weekend: "shj"` compares the calendar with Sharjah's government weekend (Friday to Sunday from 2022) instead of the country's, as `add_gulf_calendar`'s, and `fixes.addGulfCalendar` passes it on. Without `country` (or `weekend: "shj"`) the section appears only when the model already has Hijri or Ramadan columns. `country` never changes `weekStart`. DAX is not parsed: a measure whose DAX is broken is not found (Power BI Desktop shows that error). `fixes.FORMATS`: every measure and column whose number or date format is not the right one by one rule (a ratio 0.0%, a count or whole number #,0, money its own currency format, other numbers #,0.00, a date dd mmm yyyy; good formats left alone), with one script file. Optional `lang` (`ar` or `en`, 0.3.2), as `read_model`'s. |

## `add_gulf_calendar`

| Tool | What it does |
|---|---|
| `add_gulf_calendar` | The DataArcus Calendar Generator's date table for a Gulf model (the website's own generator, `assets/js/calendar-generator.js`): Hijri year, month and day, Ramadan and Eid flags and Ramadan Day, the UAE's announced Ramadan and Eid dates (for every country; later ones Umm al-Qura estimates, flagged in `Is Estimated Date`) and the country's official weekend with its change dates. Written (only with an approved `planId`; without one it checks everything and names the file) as a TMDL script to a new file next to the project, for the user to apply in TMDL view after checking Preview; nothing is written into the model and the DAX is never in the answer. `firstYear` and `lastYear` are required (the AI asks the user); `country` (`uae` by default), `weekend` (`country`, `shj` for Sharjah's government: Friday to Sunday from 2022, or a fixed one), `announced`, `lang`, `arabicNames` (Day Name (Arabic), Month Name (Arabic) and Hijri Month Name (Arabic), on by default, with the Arabic labels of the quarters, fiscal year and quarter and the flags; with `lang: "ar"` the names are Arabic already and only those labels are added), `name` (`Gulf Calendar` by default), `weekStart`, `fiscalStart`, `relateTo` (date columns to relate; only those the user names). Refuses, writing nothing, on a table, measure or column of the same name, a missing or non-date `relateTo` column, or years outside Power BI's dates or over 60. Month Name, Day Name and Hijri Month Name (and their (Arabic) columns) are sorted by their numbers in the script (`sortByColumn`, accepted by Desktop in D-GC3); marking the date table is a step by hand in the answer until a person has seen the ribbon with it in a script (D-GC2). A `relateTo` column whose type the files don't give (a DAX table's) is accepted with a note. `selfCheck` is the `gulfCalendar` check of the table the script makes (with `weekend: "shj"`, against Sharjah's rule). A Sharjah table also has `Is After Sharjah Weekend Change` (1 January 2022), as a UAE table has `Is After UAE Weekend Change`. **Optional (0.3.2), only when the user asks:** `measures` (up to 5 of the model's measures, "Table[Measure]"; each must be a measure): for each, 8 measures on the new table, the Measure Builder's own DAX from the shared `assets/js/gulf-measures.js` (`Last Ramadan`: the same Ramadan days of the Hijri year before, right on 379 of 383 Ramadan days 1439-1451 where SAMEPERIODLASTYEAR is right on none; `vs Last Ramadan %`; the Eid al-Fitr and Eid al-Adha windows, last year's and the %), the base measure's format, a name the model has never taken ("... 2"); `vat` (a `VAT Standard Rate %` column: the standard rate in force on the date in the chosen country, sourced with its change dates in `gulf-dates.js`; not the rate a sale was charged, never tax advice); `pegs` (a 6-row `Gulf Currency Pegs` table, each central bank's figure, the Kuwaiti dinar a basket with no rate; no conversion measure). The answer names them (`measures`, `vatColumn`, `pegsTable`), never their DAX or rates. |

## `generate_theme`

| Tool | What it does |
|---|---|
| `generate_theme` | A Power BI report theme (JSON), exactly as the DataArcus Theme Generator makes it: from a full palette, a brand colour and a harmony, or a preset; with the font, chart style and page. Light by default (`mode: "dark"` only when asked); a brand colour is used exactly as given (the first data colour and the accent), never changed for contrast: a failing check is said in `sayInPlan`. Without an approved `planId` it writes nothing and returns the design, the colours and a proposed `planId`; with one, the theme goes to a new file inside the DataArcus folder (never over an existing one). Returns the design for the next two tools, the readability checks and every input that could not be used. **0.3.1:** the glass look by default (`chart.look: "glass"`, also when left out); the plain look, Power BI's own cards, with `chart.look: "auto"` (or `"plain"`). Glass is used only where it keeps every text readable: otherwise the theme is plain and `look` and `sayInPlan` say why (`look.glassFailed`). The glass look: Power BI has no blur behind a visual, so it is made of what Power BI has: every visual's background in the card colour with transparency, a 1-pixel light border at the corners, a soft shadow, and a soft page picture DataArcus draws from the theme's own colours (no photo), which `create_report` puts behind every page. The transparency is lowered until text and labels stand 4.5:1 and colour 1 3:1 over the picture's darkest and lightest pixel; `glass` in the answer gives the numbers and the line for the plan. The glass theme file carries its soft picture as the page background image (`visualStyles.page["*"].background[0].image`, a data URI at the theme's page size, Microsoft's report theme schema), for pages without a background of their own; the answer never holds it. |

## `plan_layout`

| Tool | What it does |
|---|---|
| `plan_layout` | The exact position of every visual on a page (exec, analysis, ops or focus layout; KPI cards; filters; header; page size), mirrored for right to left, also as PBIR positions for editing an existing report. Writes nothing. The plan step: `limits` (slicers 3, KPI cards 6, table fields 8, page filters 8, page sizes...), and with `path` and `planFields` (create_report's `fields` shape) the plan is checked against them and the model; a plan within them gets a proposed `planId`, otherwise `planProblems` says what to change. (0.3, J14) With the model and a complete plan it builds the report `create_report` will write, with `create_report`'s own build, and checks every page of those files (`exactCheck`: Microsoft's validator offline, every field against the model, the measured rules, the layout check): `pass`, `incomplete` when a check could not run, or `blocked` (no `planId`). `pageSize.chosenBy` says whether the size is the default 1920 x 1080 or asked. `kpis` 0 to 6: fewer than 3 cards share the KPI row, 0 leaves it out. With `path` (and the plan's `fields`), the fields that lack their right format come first in the answer (`formats`), with the script file `create_report` writes after the go (the same file as `check_model_health`). With `lang: "ar"`, `arabicNames.suggestedDisplayNames` proposes an Arabic display name for each field without one from a fixed list of report words, and `proposeYourself` lists the rest for the assistant to propose in plain, short business Arabic; every suggestion is shown beside the model's name for the user to approve or edit before `create_report`, and only approved names are written (the model is never renamed). With `redesignFrom` (0.3, draft) an existing report on this model is redesigned as a copy: every page, bookmark, button, filter, tooltip page and custom visual copied file for file, with only the allowlisted changes (the top-level native visuals placed on the grid, the titles in `titles`, the custom theme's colours in `restyle`); `redesign` lists every change (page, visual, from, to), every visual not changed with why, and what is kept as it is; `create_report` with the same `redesignFrom` checks the copy (only those changes, no dangling reference, the bookmarks and filters unchanged) and writes it as "<name> redesigned" next to it; the original is never changed. **0.3.1:** `consistentText` with `redesignFrom` (off by default) gives the copy one text set: every listed native visual's own font, size, bold and italic is removed so the theme governs, and the theme gets, per class, the font and size most visuals already show (`"report"`) or keeps its own (`"theme"`), written as its visual styles per visual type (titles, axes, labels, table text: where Power BI Desktop draws them; a visual's own colour, background, alignment and wrap are kept); a report with no theme file gets one with the text set only. A definition.pbir with no `$schema` (an older Desktop save) is read by its version (4.0 or higher), said in `redesign.schemaNotes`; any other definition file without one is refused with why. `redesign.text` lists the set, each removal (page, visual, from -> to) and what is untouched with why (text boxes, shapes, images, buttons, groups, custom visuals, types DataArcus does not know). `keepPositions: true` leaves every place and size as it is. With `languages: "en+ar"` (off by default; only when the user asks for one report in English and Arabic; planned in English) the plan builds both halves, the English pages and each page's Arabic page, and `bilingual` lists every text and field with a draft Arabic for the user to approve (passed as `arabicTexts` and `arabicTerms`); the approval page draws each English page beside its Arabic page. With `sample: true`, the sample project (below). With `customVisualsFrom`, each replacement says its confidence from what was read (`confidence.levels`: high only with the custom visual's package in the report and an id naming the kind written), its evidence and, in words, what the reader no longer sees; `confidence.lead` counts them and the guesses. Where Power BI has a closer native (a bullet: columns with the target as a marker; a calendar heatmap: a matrix of months by weekday shaded by the value) it comes first and today's replacement second (`second`); `customVisualsSecond` with its key writes the second, only the user's choice. **Glass by default (0.3.1):** a new report's cards are the glass look unless the design says `chart.look: "auto"` (or `"plain"`), and only where glass keeps every text readable (else plain); the answer's `look` gives the look, who chose it (`default` or `asked`), why glass was not kept (`glassFailed`) and the line for the plan ("Glass look (default); plain: chart.look \"auto\""), which the approval page shows as "Card look". A redesign, the Arabic twin, the EN-AR copy, a native copy and hand-placed pages keep the original report's or the given theme's look. |

## `approve_plan`

| Tool | What it does |
|---|---|
| `approve_plan` | **The gate (0.2.9).** No tool writes a file without an approved plan id: `plan_layout` gives one for a report (`create_report`, with the theme inside the report), and `generate_theme` (a separate theme file), `check_model_health` (its fix scripts) and `add_gulf_calendar`, called without one, write nothing and answer with what they would write and a proposed `planId`. After the user's go, the AI calls `approve_plan` with the `planId`, then the writing tool with `planId`. **Who approves (0.2.9 rc.17):** the person, never the AI. `approve_plan` opens DataArcus's own approval window in the person's default browser, served on their computer only (127.0.0.1, a one-time secret link the AI never receives); it shows the plan (name, title, layout, fields, names, options) and every file it writes, and only their click on **Approve** approves (`approvedBy: "user-in-browser"`); **Not now** refuses. `approve_plan` waits up to 45 seconds for the click, then answers `status: "waiting"`, and the writing tools refuse until the click. When the AI app supports MCP elicitation, the app's own prompt asks instead (`approvedBy: "user-in-app"`). Nothing the AI passes approves a plan. What the window can't stop: another program on the person's computer (one that controls their browser or mouse, or another tool the AI app was given that can run commands or read the browser's history) could click it too. Unknown, expired (2 hours) or unapproved ids are refused, nothing written. A plan made from a model pins the model too (a hash of its definition files: `model.bim` or the TMDL files, a `.pbit`'s own bytes; never Power BI's data cache): a write after the model changed is refused, and the plan must be made again. The plans live in the server process only. Writes nothing. |

## `create_report`

| Tool | What it does |
|---|---|
| `create_report` | Takes `path` (the model) and an approved `planId` from `plan_layout` for the same model, nothing else (0.3.2): the plan holds the pages, fields, names and texts, and the report's name, title, theme, logo, colours and options (`plan_layout` takes them and shows them as `reportLook`); an option passed to `create_report` is refused with what to do (call `plan_layout` again to change it). The files it is made from (the theme, logo and background images, and for a native copy its source report) are approved by their contents: a file changed after the go is refused. (0.3, J14) It writes exactly the files the approved plan built and checked (`exact.digest` is the plan's); a model changed since the go is refused, and the plan is made again. A new report (PBIR) next to the user's model, every visual placed and bound to their fields, from a design (`generate_theme` or `plan_layout`) or hand-placed pages. Never touches the model or an existing report; picks a free name. Optional `displayNames` (`{ "Table[Field]": "name" }`) shows fields under other names (Arabic names for an Arabic report) without renaming the model; an Arabic report lists the shown fields still under English names (`arabicNames.missing`). Charts by month or weekday names are put in order by the report when the model has the number column. In a right-to-left report the page buttons run right to left. Never more KPI cards than the model has measures: fewer cards are built and `kpiCards` says how many and why; with no measures the charts are left out too and named. On a large model it takes `focus` or `tables` like `suggest_fields`, and refuses without one. `formats` (first in the answer): the report's fields that lack their right format, with the same script file; the report already shows them in that format (cards, the tooltip's card, tables). **0.3.1:** with `languages: "en+ar"` (off by default) and the approved plan it writes one report: the English pages and, after them, each page's Arabic page, made exactly as `create_arabic_twin` with `into: "same"` makes them (mirrored, a language button on every page, each slicer pair kept in sync, the other language's pages hidden in the tabs); only the Arabic the user approved is written. With `sample: true`, the sample project (below). |

`columnStats` (0.3.1, FX5b): counts only, the same as `suggest_fields` takes, `{ rows: { "Table": n }, distinct: { "Table[Column]": n } }` (whole numbers; COLUMNSTATISTICS()'s Cardinality, never its Min or Max); `plan_layout` takes it too and pins it with the plan. A bar or column chart's count of categories is the fewest of its Top N, what the model's metadata gives (months, quarters, days, a few known texts) and `distinct` of its category; with a count known, no bar is thicker than 36 on a 1280 x 720 page (45 at 1920 x 1080) and the space between bars is even (`categoryAxis` inner and outer padding). The sample project gives its own counts (DataArcus made its rows), unless its tables were edited. `barThickness` lists each padded chart (page, kind, categories, padding, thickness, maximum; never a category's name or value), in English and Arabic (`said`). Without a count, Power BI's own look.

## `check_report`

| Tool | What it does |
|---|---|
| `check_report` | Checks a PBIR report that already exists, whoever built it, and never changes it: Microsoft's report validator, run offline (the JSON schemas it would download are checked against Microsoft's own copies bundled in `mcp/schemas/`, MIT licence; no network connection is opened), and the rules DataArcus measured in Power BI Desktop (will a text fit its box, will a button cut its label, will Desktop ignore a formatting entry, do phone boxes overlap, will a tooltip chart need a scrollbar, a page navigator in a right-to-left report). Each finding names the file, the rule, its severity, where the rule comes from (the validator's code, or the measurement with its date and Desktop version) and a fix in words, never a patch. Each finding also has its `impact`, one of five kinds, and `impact` in the answer gives a summary and one sentence per kind: `desktopOpens` (Power BI Desktop opens the report with it; only strict validation or Fabric would refuse it: the five validator codes a working hand-built report showed, in the files where it showed them), `canBreak` (any validator code not measured in Desktop and any schema error: it can break the report in Desktop), `openedInDesktop` (0.3.1: ten validator codes, errors and warnings, counted on hand-built reports that Power BI Desktop 2.159 opened with no error on 28 Oct 2026: the validator flags the file shape, Desktop opened the report, saving in Desktop may rewrite it; each code with its measurement, never "can break"), `mayLook` (0.3.1: a validator warning Power BI Desktop was measured to draw, a text box's or a dropdown slicer's height: the part may not look as meant, never a break; each code with its measurement) and `dataarcusRule` (DataArcus's measured rules); the codes stay verbatim. Findings never quote the report's own text; `notChecked` lists what could not be judged. Optional `checks` (only some groups), `lang` and `maxFindings`. Reads a .pbip file, a .Report folder or a folder holding `definition/`; files over 8 MB and folders deeper than 12 levels are listed as not checked. The `lint` check (0.2.9) adds a design lint in its own section, read with the model the report names: a time axis sorted A to Z, bar labels likely cut, tables that grow past their width, missing titles, placeholder text, overlaps, visuals off the page; a finding that rests on a guess from names and types (not data) is marked `guess`. **0.3.1:** `FORMAT_MIXED` (a note, the `theme` check): one kind of text (visual titles, axis labels, table headers, card values...) shown in more than one font or size because visuals set their own, per page and for the report, in counts ("visual titles: 7 at 14pt, 2 at 11pt"); never a text. `lens: "arabic"` answers "Is this report ready for Arabic?" page by page instead (reading direction, texts, charts, tables, calendar names, slicers, navigation), a short summary first, each finding with its fix: a DataArcus call through approval, a setting in Power BI Desktop, or a line Power BI has no setting for. **0.3.2:** `against` (the original report, inside the working folder, on the same model) adds `sameQuestion`, the number check's layer 1: visual by visual (matched by page id and visual name), whether this report asks the model the same question, in three tiers: question (fields, aggregations, filters, sort with a Top N or a visual calculation, report measures: the numbers can differ), display (units, decimals), order (sort, the same fields in another order); "N of M visuals ask the same question; K differ (listed); L only in order; D only in display", at most 60 listed, the rest counted. Filters, slicer selections, visual calculations, report measures and bookmarks are compared by hash, said by field, type and count of literals, never returned. From the files only: it does not run the queries, so it never says the numbers are the same (layer 2 is planned). Refused for two models, a PBIR-Legacy report, a path outside the folder or a link. **0.3.3, Impact check:** `againstModel` (an earlier version of the model: a backup's or a git checkout's `.SemanticModel` folder or `model.bim`, inside the working folder) adds `impactCheck`: the report (`against` when given, else `path`) read on that model and `path` on the model its definition.pbir names (byPath; a report without one is refused), compared visual by visual in the same three tiers: which visuals can show another number, each with its reasons and the chain of names from the visual's own field to what changed ("[Margin %] uses [Net Revenue] uses [Returns Value]: measure: its DAX changed"), and how many can only show other numbers if the data changed. It follows the measures a visual calls, their columns and tables (a table's source query included), and the relationships a filter can travel between them; a format string or a colour set by a measure is display, a sort-by column order; a changed row-level security role is said once for the model. In doubt a visual counts as able to show another number (a model file not read fully: no visual is said unchanged). At most 60 visuals listed, every one counted (`notListed`), the section within 16,000 characters. From the files only: no query is run; the data, row-level security per person, a custom visual's own logic and what a DAX text builds at run time are outside it, and the relationship rule is Microsoft's documented filter propagation, not measured in Desktop (`notProved` says so). **0.3.3, like for like in the Gulf:** `likeForLike: { year, country }` (both optional; `country` one of `uae`, `ksa`, `kwt`, `qat`, `bhr`, `omn`, `shj`; not with `lens`) adds `likeForLike`, read on the model the report's definition.pbir names (one reading, shared with `againstModel`): the visuals whose number passes through a comparison with the same Gregorian dates of another period (`SAMEPERIODLASTYEAR`, `DATEADD`, `PARALLELPERIOD`, `PREVIOUS*`, `NEXT*`, in a measure, a report measure or a calculation group's item the visual reaches through the group's column), each with its chain of names; the comparison measures and how many visuals show each; the "<base> Last Ramadan" measures the model lacks (the DAX Measure Builder's names, given whole to 200 characters); and, for the year, each month compared with the month it is set beside: its Ramadan, Eid al-Fitr and Eid al-Adha days and, with a country, its weekend and VAT rate, where they differ. Without a year, how many months differ in each year DataArcus keeps dates for (2018 to 2030). A date not announced yet is the Umm al-Qura calendar's estimate and is marked. It says "not like for like", never "wrong": whether the business moves with Ramadan is the person's to know. At most 60 visuals, 60 measures, 60 missing names and 4 distances listed, every one counted; the section within 16,000 characters. **0.3.3, the brief check:** `briefCheck`, on the model the report's definition.pbir names (the same one reading as `againstModel` and `likeForLike`; the model loaded once a call), on every check when `checks` is not narrowed, and whenever `brief` is given: for each visual, each number it shows and each column it groups by, whether a filter on that column can reach a table the number reads (through the relationships, from their one side to their many side, both ways when the relationship says so, or because the number's DAX names that table). When none can, every row of that column shows the same number: a finding "one value on every row", with why; a number that reads no table is `constant` (never a finding); a column of a field parameter or a calculation group, and a report measure whose definition was not read, are `cannot tell`; a name the model lacks is listed apart. A report measure is judged by what its DAX reads. In doubt it says "cannot tell", never accuses: `USERELATIONSHIP` or `CROSSFILTER` anywhere under a number makes every relationship count, both ways, active or not. `brief: [{ id, measure, by }]` (at most 60; `measure` "[Revenue]" or "Revenue", `by` names like "Calendar[Month]" or "'Store'[Region]", [] for a total; not with `lens`) adds `questions`: `answered` (a visual groups the measure by exactly those columns; a visual grouped by them and more is answered too, worded `how: "answers it, split further"`, with the extra columns in `splitBy`), `partly` (the measure is shown, grouped otherwise), `not answered` (the model can, no visual does) or `cannot answer` (a name not in the model, or a column that cannot move the measure; the visuals that show it anyway named); a `by` name that is not a column is `not read`.
