## Plan (written before any code or run)

### What the code says (read before planning)
- The shared engine `assets/js/report-mirror.js` mirrors a matrix (`pivotTable`) only by reversing its Values
  projections (line 253), so a matrix with one measure is not changed at all apart from its place and title alignment:
  that is the owner's case (one measure, months across). Its row headers stay left, its months run left to right.
- `create_report` never writes a Columns field on a matrix (`pbip-query.js` bindQuery `matrix`: Rows = the first text
  field, Values = the measures), and in Arabic does not reverse the measures (no right-to-left code for a matrix).
- What Microsoft's capabilities give a matrix (`@microsoft/powerbi-core-visual-schema`, the version `mcp/package.json`
  pins, `data/capabilities.json` `pivotTable`; the file is one line, so properties are cited by their path in it):
  roles Rows, Columns, Values; `sorting: { default, custom }`; `dataRoleTotals` for Rows and Columns; no property named
  for direction, right to left or text direction (to be confirmed by a search of every visual's capabilities).
  Candidates: `general.layout` (Compact / Outline / Tabular), `rowHeaders.alignment`, `rowHeaders.stepped`,
  `columnHeaders.alignment`, `columnHeaders.titleAlignment`, `values.valuesOnRow` ("Show values in row groups rather
  than columns"), `subTotals.rowSubtotals`, `subTotals.rowSubtotalsPosition` (Top / Bottom), `subTotals.columnSubtotals`
  (no position for column totals), `subTotals.perRowLevel` / `perColumnLevel`, `columnFormatting.alignment` with
  `styleHeader` / `styleValues` / `styleSubtotals` / `styleTotal` (per measure, selector `metadata`); the values card has
  no alignment of its own. Instance selectors (`data/instance-selectors.json`): `subTotals` takes Row / Column.
- The query (`mcp/schemas`, visualConfiguration 2.1.0, the version visualContainer 2.1.0 references): `sortDefinition`
  is a list of `{ field, direction }` (SortDefinition line 77, QuerySort line 94); a projection has no sort of its own
  (RoleProjection line 166: field, queryRef, nativeQueryRef, displayName, format, active, hidden).
- The paths that write Arabic visuals (to be shown per kind in this file, "One engine"):
  1. `create_report` with lang "ar" (designed pages and hand-placed pages alike): `pbip-export.js` -> `pbip-page.js`,
     its own right-to-left code: `pbip-query.js` `mirrorChart` (bar, column, line), `visual-gallery.js` `mirrorSort` and
     the gallery's `mirror` axis lines (combo, small multiples), the table's own reversed fields (`tableFields`,
     `rowLabelOf`), the pills' sort, the card's margins and image side, titles and text boxes by `align`.
  2. `create_arabic_twin` (a separate twin) and 3. `create_arabic_twin into:"same"` (the EN-AR copy): both build the
     Arabic pages in `arabic-twin.mjs` `buildTwin` through `Mirror.mirrorPage` with the same options; the plan
     (`planTwin`) calls `mirrorPage` too.
  4. The redesign (`redesign.mjs`) and its overlay copy no visual into Arabic (no right-to-left code): not a path.
  5. X2's bilingual create_report is not on this branch (a later wave).
- Differences read in the code between create_report's Arabic and the twin's mirror of the same English visual
  (expected red in the parity suite): column and line charts and the gallery's combo and small multiples write
  `categoryAxis.invertAxis` on a categorical axis (the engine never does: Desktop ignored it there); a chart sorted by
  its measure is always made Ascending (the engine turns the sort round, the same for a Descending one); charts with a
  legend role get no legend position (the engine puts it at the right); the matrix's measures are not reversed; the
  table is built for right to left from its fields (a hidden name column first so "Total" shows, the text column at the

## What Power BI allows for a matrix (from the schema; no Desktop claim)
- Microsoft's capabilities (`@microsoft/powerbi-core-visual-schema`, the version `mcp/package.json` pins) have **no
  right-to-left, direction, reading-order or text-direction property** for a matrix (`pivotTable`) or a table
  (`tableEx`). A search of every visual's properties for rtl / right to left / direction / bidi / mirror / reverse
  finds only a chart's "Reverse order" of its series (`layout.seriesOrderReversed`), a combo's or area's stack order,
  slicer and card overflow direction and the KPI's goal direction: nothing that reads a matrix from the right.
- What can change how a matrix reads (each written by the lab, page 2-6): the sort of its column field
  (`query.sortDefinition`, a list of `{ field, direction }`; `pivotTable.sorting` lists default and custom sorting), a
  model column sorted by a reversed key (no report property), totals (`subTotals.rowSubtotals`, `rowSubtotalsPosition`
  Top / Bottom, `columnSubtotals`: there is **no position for column totals**), alignment (`rowHeaders.alignment`,
  `columnHeaders.alignment` and `titleAlignment`, `columnFormatting.alignment` per measure; the values card has none),
  `rowHeaders.stepped`, `general.layout` (Compact / Outline / Tabular), `values.valuesOnRow`, and the roles themselves
  (months in Rows: transposed). None of them moves the row headers to the right: only the laptop can say whether a
  Descending month order with right-aligned headers reads as right to left to an Arabic reader.

## Decisions I made
1. **The lab writes its own made-up model** (facility service requests, two tables: 24 and 12 months), not
   `service-orders`: that model has no Arabic or long names, no second row level, and one month table. A model.bim with
   typed Power Query rows (the pills lab's shape), so it opens with data after one Refresh.
2. **More pages than the brief's 7:** the combinations are 2 matrices a page (5a-5c at 1280 x 720, 6a-6c at 1920 x 1080),
   so each is wide enough to judge; pages 1-4 are 1280 x 1080 to hold 6 or 8 matrices at a readable size. 11 pages, 41
   visuals.
3. **The lab's twin and combination variants are written by the engine itself** (`report-mirror.js` matrixRtl), so
   what the laptop proves is exactly what a path would write; each keeps its own cell of the lab's grid (the twin would
   move it to its mirrored place on the page, which is not what is judged).
4. **The engine's matrix switch has 5 values** (`MATRIX_RTL`: values (today, the default), none, columnsDescending,
   alignRight, columnsDescendingAlignRight); the other variants (totals, layout, values on rows, transposed) are lab-only
   properties, not engine options, until the laptop shows one is needed. Nothing sets the switch but the lab
   (parity E5).
5. **One engine for the charts, not for everything:** create_report's writer now calls the engine for every chart
   (bar, column, line, combo, small multiples, a kept waterfall, the tooltip pages' bars, the metric switcher) and its
   own chart code is gone (`pbip-query.js` mirrorChart is a call to the engine; `visual-gallery.js` lost its mirror lines
   and `mirrorSort`). Its new cards, slicers, pills, text boxes and Reset button are built for right to left by the
   writer and come out equal to the twin's (the parity suite compares them), so they were left in place. Its **table**
   is a different design on purpose (the first text column first so the total row says "Total", round 10; the hidden
   name column, round 23) and its **matrix** keeps its measures in order until the laptop's pick (brief: nothing new for
   the matrix): both listed in the test as INTENDED with why.
6. **Continuous axes:** the writer passes the engine every date and number column it knows (the model's types, the
   bound fields' own) as continuous, so a chart over a date or a number keeps its `categoryAxis.invertAxis` (round 13:
   "both are written, and Desktop reversed such an axis once"); on a text axis it is no longer written (Desktop ignores
   it there; the twin never wrote it). The twin still passes its date columns only (Seen, not in scope 3).
7. **The website shares the engine:** I first read the Theme Generator as never mirroring charts; the website's pbip
   suite proved that wrong (its Arabic download with the person's own model asks `chartAxes: 'mirrored'`,
   theme-generator.js line 658, and no download came: `report-mirror.js` was not loaded in the browser). Now
   `report-mirror.min.js` exists (new) and the Theme Generator's writer list loads it after `visual-types.min.js` and
   before `pbip-query.min.js` (?v= 20261025m1); parity E6 guards the order. The sample download (no model) keeps its
   charts as they were (test.mjs round 13, item 10).
8. **Deliberate test moves, said in words:** gallery T, gallery-reachable HA, metric-switcher A4 and `test.mjs` round
   13 `mirroredUp` read the writer's old `categoryAxis.invertAxis` on a categorical axis; each now reads the engine's
   rule (none on a categorical axis, the sort Descending; on a date axis it stays required).
9. **The parity suite's W side is the writer** (`pbip-export.js` build, what create_report calls for designed and
   hand-placed pages alike) on mirrored slots, not create_report through the server: the server adds no mirroring after
   the build; T and C go through the server with the approval clicked.
