## Plan (written before any code or run)

### What the code says (read before planning)
- The shared engine `assets/js/report-mirror.js` mirrors a matrix (`pivotTable`) only by reversing its Values
  projections (line 253), so a matrix with one measure is not changed at all apart from its place and title alignment:
  that is the owner's case (one measure, months across). Its row headers stay left, its months run left to right.
- `create_report` never writes a Columns field on a matrix (`pbip-query.js` bindQuery `matrix`: Rows = the first text
  field, Values = the measures), and in Arabic does not reverse the measures (no right-to-left code for a matrix).
- What Microsoft's capabilities give a matrix (`@microsoft/powerbi-core-visual-schema`, the version `mcp/package.json`
  pins, `data/capabilities.json` `pivotTable`; the file is one line, so properties are cited by their path in it):
  roles Rows, Columns, Values; `sorting: { default, custom }`; `dataRoleTotals` for Rows and Columns; no property named
  for direction, right to left or text direction (to be confirmed by a search of every visual's capabilities).
  Candidates: `general.layout` (Compact / Outline / Tabular), `rowHeaders.alignment`, `rowHeaders.stepped`,
  `columnHeaders.alignment`, `columnHeaders.titleAlignment`, `values.valuesOnRow` ("Show values in row groups rather
  than columns"), `subTotals.rowSubtotals`, `subTotals.rowSubtotalsPosition` (Top / Bottom), `subTotals.columnSubtotals`
  (no position for column totals), `subTotals.perRowLevel` / `perColumnLevel`, `columnFormatting.alignment` with
  `styleHeader` / `styleValues` / `styleSubtotals` / `styleTotal` (per measure, selector `metadata`); the values card has
  no alignment of its own. Instance selectors (`data/instance-selectors.json`): `subTotals` takes Row / Column.
- The query (`mcp/schemas`, visualConfiguration 2.1.0, the version visualContainer 2.1.0 references): `sortDefinition`
  is a list of `{ field, direction }` (SortDefinition line 77, QuerySort line 94); a projection has no sort of its own
  (RoleProjection line 166: field, queryRef, nativeQueryRef, displayName, format, active, hidden).
- The paths that write Arabic visuals (to be shown per kind in this file, "One engine"):
  1. `create_report` with lang "ar" (designed pages and hand-placed pages alike): `pbip-export.js` -> `pbip-page.js`,
     its own right-to-left code: `pbip-query.js` `mirrorChart` (bar, column, line), `visual-gallery.js` `mirrorSort` and
     the gallery's `mirror` axis lines (combo, small multiples), the table's own reversed fields (`tableFields`,
     `rowLabelOf`), the pills' sort, the card's margins and image side, titles and text boxes by `align`.
  2. `create_arabic_twin` (a separate twin) and 3. `create_arabic_twin into:"same"` (the EN-AR copy): both build the
     Arabic pages in `arabic-twin.mjs` `buildTwin` through `Mirror.mirrorPage` with the same options; the plan
     (`planTwin`) calls `mirrorPage` too.
  4. The redesign (`redesign.mjs`) and its overlay copy no visual into Arabic (no right-to-left code): not a path.
  5. X2's bilingual create_report is not on this branch (a later wave).
- Differences read in the code between create_report's Arabic and the twin's mirror of the same English visual
  (expected red in the parity suite): column and line charts and the gallery's combo and small multiples write
  `categoryAxis.invertAxis` on a categorical axis (the engine never does: Desktop ignored it there); a chart sorted by
  its measure is always made Ascending (the engine turns the sort round, the same for a Descending one); charts with a
  legend role get no legend position (the engine puts it at the right); the matrix's measures are not reversed; the
  table is built for right to left from its fields (a hidden name column first so "Total" shows, the text column at the
  right) where the engine reverses every column.

### Part A: the lab (`mcp/lab/matrix-mirror.mjs <empty folder>`)
One project, "Matrix Mirror Lab", on its own made-up model (facility service requests; no employer data): a model.bim
with typed Power Query rows (the night of 6-7 Oct fact): `Requests` (8 service types x 24 months = 192 rows) and
`Requests 12m` (the last 12 months, 96 rows); columns: Service Type (8), Service Type AR, Service Type Long (long
English), Service Type AR Long, Group and Group AR (2, for two row levels), Month Start (date), Year, Month and Month AR
(sorted by Month Key), Month Desc and Month AR Desc (the same texts sorted by Month Key Desc, minus the key), Month Key,
Month Key Desc, Amount, Requests; measures Amount and Requests on each table. Every matrix's title is its variant id and
what it sets. Pages:
1. Baselines: B1 the English matrix as create_report writes it (`pbip-export.js` build, the lab's fields), B2 B1 through
   the twin today (`Mirror.mirrorVisual`), B3 the owner's shape in English (service type in Rows, months in Columns, one
   measure, totals on), B4 B3 through the twin today (not mirrored: the owner's case), B5/B6 B3 and B4 with two measures.
2. Column order: C1 `sortDefinition` Month Descending; C2 Service Type Ascending then Month Descending; C3 the reversed
   sort column (Month AR Desc in Columns); C4 Year and Month in Columns, both Descending; C5 Month Key (not in the visual)
   Descending; C6 two measures reversed (today) with months across.
3. Totals: T1 row subtotals at the Top (two row levels), T2 at the Bottom, T3 column subtotals off, T4 row subtotals off,
   T5 both off, T6 C1 with column subtotals on (where the Total column goes when the months run Descending).
4. Row headers and layout: H1 row headers right-aligned, H2 column headers and their title right-aligned, H3 values
   right-aligned (`columnFormatting.alignment` per measure, applied to header, values, subtotals, total), H4 stepped off,
   H5 layout Tabular, H6 layout Outline, H7 values on rows (two measures), H8 transposed (service type in Columns, months
   in Rows).
5. Combinations, 1280 x 720: X1 C1 + every alignment right + Arabic names, 12 months; X2 X1 with 24 months (scrolls);
   X3 X1 with the long Arabic names; X4 X1 with the long English names, English labels; X5 C3 + every alignment right,
   24 months; X6 H8 + every alignment right.
6. The same six at 1920 x 1080.
7. The table reference: R1 a table of the same data (service type, Amount, Requests) as create_report writes it in
   English, R2 its twin today (columns reversed: what "mirrored" looks like), R3 a table by month mirrored by the twin.
Every variant names its property, JSON path and source in `mcp/work/M1.md` ("Variants"). Microsoft's validator: 0
errors on the lab project (the lab runs it and prints the count). "For the laptop": the list to judge per variant.

### Part B: one engine
1. "One engine": per path, per visual kind, the function that mirrors it (table in this file).
2. `mcp/test-0.3.1-mirror-parity.mjs` (in `npm test`, one result line): one English report with every kind (card, new
   card, bar, stacked bar with a legend, column, line, combo, waterfall, donut, table, matrix, slicer, pills, text box,
   button, image, shape, group) on the made-up `service-orders` model, made Arabic by (W) create_report's writer in
   Arabic on the mirrored slots, (T) the separate twin and (C) the EN-AR copy, through the server with the approval
   clicked as a person does. Per kind: W vs T and C vs T compared on position, alignment, order, projections, sort and
   formatting (objects and container objects), after taking out what is meant to differ, each listed in the test with
   why (the Arabic texts, the visuals' names and the copy's page ids, the twin's fitted widths, the language button,
   the writer's own table design and the matrix until the laptop's pick).
   Expected before the change (from the code above): W vs T red for column, line, combo (invertAxis on a categorical
   axis), stacked bar (legend); green for bar, new card, donut, waterfall (native, as the default), slicer, pills, text
   box, image; C vs T green for every kind (one buildTwin). Engine checks (E): red for the writer delegating to the
   engine and for the matrix lab switch.
3. Then every path calls the engine: the writer's `mirrorChart`, `mirrorSort` and the gallery's mirror axis lines are

   After: every parity check green; every other suite's count unchanged except where a check reads the writer's
