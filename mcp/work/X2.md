## Design (decided)
- Inputs on plan_layout and create_report (pinned like every look option, REPORT_LOOK; left out at create_report, the
  plan's value is written): `languages: "en+ar"`; `tabsShown: "en" | "ar"`; `arabicTexts: { "<English text>": "<Arabic>" }`
  (by the text itself: a build draws new page ids and visual names each time, so the twin's ids can't be kept between two
  plan_layout calls); `arabicTerms: { "Table[Field]": "<Arabic>" }` (J18's terms, as the twin takes them).
- `lang` must be English (the Arabic half is built from the English pages): `languages` with lang "ar" is a plan problem.
- plan_layout's exact artifact (J14): the English report built in memory, then X1's planTwin (into "same") on those
  files through the reading block's memorySource (arabic-twin.mjs gets a memory location beside its disk one: no second
  reader), the report's own name kept (no " (EN-AR)" suffix: it is a new report); the combined files replace the
  English ones in the artifact, checked (validator, references, measured rules, lint) and digested; create_report writes
  exactly them. The model's scripts (format, switcher, flip cards, status icons) are the English build's, written once.
- The answer: `bilingual` (pairs, buttons, syncGroups, tabs, texts deduped by text with draftArabic and the approved
  Arabic, terminology sheet and askNext, notTranslated, cannot); the plan's data: the same for the approval page; the
  terminology rows remembered at the write as for an Arabic plan.
- No Arabic month script in this mode (arabicMonth false: the month names are data, as in the English half; said).
- Sync: a slicer kind syncs when Microsoft's visual catalog (@microsoft/powerbi-core-visual-schema, pinned) says
  `supportsSynchronizingFilterState`: slicer, advancedSlicerVisual (pills), listSlicer, textSlicer. X1's copy follows.
