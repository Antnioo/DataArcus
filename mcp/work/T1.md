## Plan
1. This plan, pushed first.
2. `mcp/test-0.3.1-mutation.mjs` (in `npm test`, last; a standalone script, so CI's shard 0; one result line
   `PASS  mutation  N checks (M mutants, all killed)`). For each mutant: copy `mcp/` (its `node_modules` linked, not
   copied) and `assets/js` + `assets/data` into a temp folder, apply one small text change to ONE source file of the copy
   (the change must match exactly once, and the file must still parse: `node --check`), run the existing suites that
   guard it (`cwd` the copy's `mcp/`), and require at least one to fail: killed. The repo's files are never edited.
   Why a copied tree and not an env var or a hook: the suites already find the server and `lib/` from their own folder
   (`import.meta.url`), so a copy runs them unchanged against the mutant, with no test-only hook in product code and no
   loader trick; the copy is the closest thing to the real file being wrong.
   - N = M kills + one baseline per guard suite used (each guard must PASS on the unmutated copy first, or a kill means
     nothing) + M "applies once and parses".
   - 4 workers, each with its own copy; a mutant's file is restored before the next mutant. Default: a mutant stops at
     its first failing guard. `DA_MUTATION_ALL=1` runs every guard of every mutant (for this file's results table).
     `DA_MUTATION_ONLY=<id,id>` runs some.
   - No network; deterministic (fixed list, no random mutants). Expected under 3 minutes on Linux.
3. A surviving mutant is a real finding: the missing test goes in the suite that owns that block (red with the mutant,
   green without), said here as a deliberate addition. If closing it needs product code, that item stops and is reported.
4. `node scripts/check-result-lines.mjs`; the full `cd mcp && npm test` once; WORK.md; results below.

## Decisions I made
1. **A copied tree, not an env var or a hook.** The suites find the server and `lib/` from their own folder, so a copy
   (`mcp/` with its node_modules linked, `assets/js`, `assets/data`, `scripts/tests`) runs them unchanged against the
   mutant; no product code learns about mutation testing. `scripts/tests` was added after the first run: seven guards
   read the website's fixtures from it and crashed on the copy (they were never counted as kills).
2. **A mutant is killed only by a failing check:** a guard must PASS on the unmutated copy first (29 baselines), the
   mutant's text must be found exactly once and still parse, and a guard that times out kills nothing. A mutant whose
   code moved fails loudly (S9 moved one: the dry run named it).
3. **test.mjs is not a guard.** Its shards take minutes each; four mutants were killed only by its parts, so each got
   a fast check in its owning standalone suite instead (said in the table), to keep the run under 3 minutes.
4. **The golden baseline is not a guard:** on the copy, under the four workers' load, it reported 6 differences without
   any mutant (it passes alone): a kill by it would mean nothing. V-rows is killed by test-0.2.9d's new check.
5. **Windows drive and UNC paths:** no path mutant runs for them on Linux, where Node's `path` has no such form; their
   screen pattern in names (S-path) is mutated and killed. D-nfc / D-nfd run on Linux and Windows only (macOS keeps one
   folder for both forms, so normalising changes nothing there).
6. **Severity flips:** check_report's "can break" comes from a finding's origin, not its severity, so flipping a rule's
   severity never moved it into "can break" (the guards checked the split, not the severity). The new checks pin the
   severity and the impact of each rule mutated.
7. The suite's area in `tests.json` is the reviewer's "core" (from `pending`), kept.
8. S2b moves the replaced file away instead of deleting it: a deleted file's inode number can be given at once to the
   next new file, and then nothing tells the two apart (Seen 1).

## Seen, not in scope
1. **The rollback's identity check can be fooled by inode reuse (a real limit, product code: not fixed here).** When
   another program deletes a file DataArcus just wrote and writes one of the same size at the same name before the
   clean-up, Linux may give the new file the freed inode number: dev+ino and size then match, and the rollback removes
   the other program's file. Found when S2b, written first with delete-and-write, failed without any mutant. A content
   hash taken at the write (as the answers file already does) would close it. Needs the owner's go.
2. **Defence in depth that no tool can reach** (G-artifact, W-free-real, and, before this branch, D-inside /
   D-underRoot-any, where real() catches what underRoot lets by): kept, as said under "Equivalent"; no change proposed.
3. **test.mjs's parts are the only guard of some behaviour** (four mutants above, before the fast checks): the
   reviewer may want such checks moved into standalone suites over time, so a mutation run stays fast.
4. **The golden baseline is load-sensitive:** 6 differences on a copied tree under four parallel workers, none alone.
   Not investigated here (cause unknown: its answers or its timing); worth a look before CI runs it beside other jobs.
5. **The known-gap path is dead with today's catalog** (U1: the catalog lists the slicer's dropdown), so only a unit
   check (test-0.2.9-a4 T1) guards impactOf's known branch.
