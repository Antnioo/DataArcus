## CHANGELOG line
- Every DataArcus theme (generate_theme, create_report, the website's Theme Generator) carries three status icons in
  its `icons` block, "daGood" (a tick in a circle), "daWarn" (a triangle with "!") and "daBad" (a cross in a rounded
  square): they differ in shape as well as colour, coloured from the theme's good / neutral / bad (taken to 3:1 on the
  visuals' background, hue kept), unused unless a rule names them. plan_layout and create_report take `statusIcons`
  (off by default): `true` puts an icon before each table or matrix measure that is a rate or ratio whose target the
  model's metadata names (a measure "<name> Target / Goal / Budget"), by a status measure written as a TMDL script next to
  the project ("<report> - status icons.tmdl", at or above the target good, below it bad; the model never changed by
  DataArcus); `[{ measure, good: ">= 0.97", bad: "< 0.94" }]` uses the user's own thresholds as rules (no measure, no
  script). Thresholds are never guessed. Pinned by the plan, on the approval page; check_report knows the icons (a note
  until the script is applied; the shapes carry the meaning, said in the a11y notes). (L5)

## Decisions I made
- **The icons are in every theme** (design-engine.js `buildTheme`, so generate_theme, create_report and the website's
  Theme Generator get the same block): Microsoft's validator lists `icons` among a theme's known root keys
  (`THEME_ROOT_PROPS` of the version mcp/package.json pins), the lab drew them, they are unused until a rule names them,
  and a user of the website's theme can pick them in their own conditional formatting. One theme whether the option is
  on or off (the option changes visuals and adds a script, never the theme). The theme suites change on purpose (listed
  under Results). A theme the user passes (hand-placed pages) gets the three icons in the report's copy only when
  `statusIcons` is on and the theme has no icon of those names (the user's file is never changed; said in the answer).
- **Colours**: the theme's good / neutral / bad, each taken to 3:1 against the visuals' background with the engine's
  own `toContrast` (hue kept; unchanged when it already stands 3:1: WCAG 1.4.11 for a graphic), written as `rgb()`; the
  mark inside (tick, "!", cross) in white or near black (#1f2329), whichever stands higher on the fill (a dark theme's
  text is light, like its warning yellow, so the text colour would vanish on it). No `#` inside
  a data URI. The SVG's numbers are fixed (16 x 16), so the three are always three distinct shapes.
- **Option** `statusIcons`: `true` (automatic) or a list of 1-8 `{ measure: "Table[Measure]", good?, bad? }`.
  - Both `good` and `bad` given (`>=`, `>`, `<=`, `<` and a number): **Way E**, rules only, the user's numbers exactly;
    between the two the warning icon. The two must point opposite ways and not overlap (else a plan problem).
    Only one of them given: a plan problem (no threshold is invented).
  - No thresholds: **Way C**: needs a target measure the model's metadata names for it (same table first: "<M>
    Target", "<M> Goal", "<M> Budget", "Target <M>", "Goal <M>", "Budget <M>", any case; then the other tables). The
    status measure "<M> (status icon)" returns "daGood" when the value is at or above the target, "daBad" below it,
    blank when either is blank: two states, no warning band (a band would be a guessed threshold). A measure without a
    target: a plan problem naming why.
  - `true`: Way C for every measure in the report's tables and matrices that is a rate or ratio (the picker's own
    `isPercent`: a percent format, or "rate/ratio/share/margin/%" in its name) and has a target; none found: told, no
    icon, not an error.
  - A listed measure that is not in any table or matrix of the report: told (`statusIcons.notShown`, with why), not an
    error.
  - Way D (an SVG measure) is not used: the theme carries the shapes once.
  - A model KPI (TMSL `kpi`) is not read: the TMDL reader does not read KPIs, and their target is DAX the plan would
    have to copy into the script (Seen, not in scope).
- **The model is never changed**: Way C's measures go into ONE script "<report> - status icons.tmdl" (createOrReplace,
  `ref table`, folder "DataArcus status icons", lineage tags and free names from mcp/lib/model-script.mjs, the file
  joins the report's one write and the plan's digest), as L3's and L4's.
- **In REPORT_LOOK** (pinned, filled from the plan, another value at create_report refused) and **LOOK_DEFAULTS**
  (`false`).
- **Which visuals**: tables (`tableEx`) and matrices (`pivotTable`) the writer makes; the entry goes into the visual's
  `objects.values` exactly as the lab's (matchingOption 1: rows, not the total).
- **Right to left**: the layout 'Before' in both languages (the lab's proven value). Power BI does not mirror a table:
  'Before' is at the left of the number, which reads after it in Arabic; the other value (right of the number) is not
  proven, so it is a laptop check, not written. The twin copies the entry as it is.
- **Accessibility**: a new note in check_report's a11y family (`A11Y_ICON_SHAPES`, report-a11y.js): a table or
  matrix whose icons are the theme's DataArcus icons: "the icons differ in shape, colour is not the only signal" (a
  note); icons named that the theme does not have, or that share one shape: a warning.
- **check_report**: `ICON_MEASURE_PENDING` (a note, a DataArcus rule) when a Way C status measure is not in the model
  yet; never "can break". The preview draws a small marker before the icon column's values.
