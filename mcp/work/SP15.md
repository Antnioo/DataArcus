## Decisions I made
- **The index is frozen** (not only proven unwritten): buildIndex returns `Object.freeze`d object whose five Maps have
  `set`, `delete` and `clear` replaced by a function that throws, then are frozen; `K` is frozen too. Readers (`get`,
  `has`, iteration, `size`) are untouched, so analyze() is identical (N1-N14, sp9). I2 also proves from the source that
  the engine never writes to `IX`. The normalised model (M) is not frozen: it is the model's data the rules read, and
  freezing it deeply would cost time on every check for no caller that needs it; no code writes to it today.
- `lc`, `text` and `uniq` are copied into model-index.js as private one-line helpers (as SP9 did for `text`); the engine
  keeps `lc` and `uniq` and no longer needs `text`.
- model-index.js requires dax-reference-parser.js itself (daxRefs needs `tokenizeDax`), the same way the engine does,
  so the Node loaders need no change (SP9 gave them a `require` that loads the neighbour).
- On the base, sp15 reads the engine's private functions by loading its file with them added to its API (the file on
  disk unchanged): the only way to record buildIndex and aggBase before the move.
- sp9's made-up models moved to `mcp/fixtures/health-models.mjs` (one place for both suites, D-1016-01); sp9's records and
  checks unchanged. The B3 incomplete project is made there too, beside sp9's.
- After the first recording I added one measure to B2 (a virtual column named like a measure), because a mutation went
  uncaught; the records were recorded again on the base code (a worktree at 790d07d), never on the split.
- Stamps: one new stamp `20261103sp15` for model-index, the engine, the worker (in model-health.js and
  theme-generator.js), model-health.min.js (both tool pages) and theme-generator.min.js (three generator pages).
