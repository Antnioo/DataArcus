## Decisions I made
- The store's get() is the live design (the page changes it in place, as before); a whole new design (the example,
  Undo) goes through replace(), which tells the subscribers; theme-generator.js rebinds its `state` by subscribe.
  Rewriting every change as update(fn) would change the order of the page's writes for no gain in a move.
- Every script stamp stays in theme-generator.js: the loaders moved out of the project card's block to the top level
  of the page code (defining them loads nothing), and the download module gets them as `loaders`. The other splits'
  stamp bumps (SP27, SP29, SP30) therefore land in theme-generator.js as before.
- The illustrative previews (the sample thumbnail, previewMarks, bgSvg) stay in theme-generator.js, as the brief
  names only the three modules; the layout and download modules get bgSvg as a hook.
- The moved code was re-indented by two spaces except inside template strings (their text is the page's markup):
  sp31 caught the first attempt, which added spaces inside them. A literal-by-literal comparison of the base file
  with the four files (espree tokens) differs only in the modules' wrappers and the page-size message's reset.
- Source readers whose pinned text moved (sq13 `PV.fromFiles`, pbip `relationships: e.relationships`, v029w
  `fitSlots`) and the "never anywhere in the page" pins (v029design kpiCards, rx="18", the derived colours; ts1;
  sq14's month lists) read the generator's four files through `mcp/test-source.mjs` `generatorSource()`, as the
  twin's and the server's readers do; no expected number changed.
- One stamp `20261104sp31` for the three new .min.js and theme-generator.min.js on the three pages.
