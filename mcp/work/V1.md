# V1: a VS Code extension prototype for the DataArcus MCP (B-194)

Branch `feat/vscode-extension` from `origin/integration/0.3.0-wave` (95302c5). Cloud builder, 20 Oct. Kept out of
0.3.0 (the reviewer opens a later draft PR). Never published: the Marketplace publisher and the publish click are the
owner's.

## CHANGELOG line
- V1 (B-194, prototype, not released): `vscode/`, a VS Code extension that registers the bundled DataArcus MCP server
  with VS Code's MCP support (stdio, the workspace folder as `DATAARCUS_ROOT`, no telemetry, no network of its own);
  `vscode/RESEARCH.md` on what VS Code supports and the Marketplace steps. Packaged locally only, never published.

## Plan (written before any run)
1. This file, pushed first.
2. `vscode/RESEARCH.md`: VS Code's MCP support (the contribution point and API, the minimum version, what the person
   sees and approves, the gallery and `mcp.json`), how stdio servers run, elicitation (our approval prompt) and the
   browser window, shipping Node and the server, the Marketplace (publisher, verified domain, licence and privacy
   fields, the install count), competitors (names and install counts only). Links, Microsoft's own docs first.
3. The prototype, plain JS, no bundler, everything in `vscode/`:
   - `package.json`: `contributes.mcpServerDefinitionProviders` (id `dataarcus`), no `activationEvents` on `*`
     (the provider's own activation event is implied), `engines.vscode` the first version with the stable API,
     settings `dataarcus.workingFolder` and `dataarcus.nodePath`, disabled in untrusted and virtual workspaces.
   - `lib/definition.js`: the server definition as a pure function (testable without VS Code): the command, args,
     `DATAARCUS_ROOT` (the setting, else the first workspace folder, else none: the server then refuses every tool and
     says why), cwd.
   - `extension.js`: registers the provider, re-announces on folder or setting changes. No telemetry, no network.
   - `scripts/stage.mjs`: copies the server into `vscode/server/` with the repo's own layout (`mcp/server.mjs`,
     `mcp/lib/`, `mcp/schemas/`, `mcp/package*.json`, and only the `assets/` files the server's import graph reaches),
     then `npm ci --omit=dev` there. The staged folder is not committed.
   - `README.md` (Marketplace page), `CHANGELOG.md`, `LICENSE` (the repo's), `.vscodeignore`.
4. Tests `vscode/test/*.test.mjs` (node:test), written before the code they check: the manifest (provider declared,
   no `*` activation, no telemetry package or setting, untrusted workspaces off), the definition (bundled server path,
   `DATAARCUS_ROOT` = the workspace folder or the setting, none without a folder), the staged import graph complete
   (every relative import of the staged server resolves inside `server/`), `vsce ls` lists only the intended files.
   Not added to `mcp/package.json`'s test list: the brief keeps every change inside `vscode/` (the vscode suite has
   its own `npm test`; result line `PASS  vscode  <N> checks`).
5. `vsce package` (never `publish`); the `.vsix` size recorded. Headless VS Code (@vscode/test-electron) if the
   container allows it; otherwise what only a person can check.
6. Report and this file's results.

Expected (before any run): every vscode test red before the code (no files), green after; the server started from
the staged folder answers `tools/list` with 11 tools; the `.vsix` about 8-12 MB (the `.mcpb` 0.2.7 was 8.97 MB; the
validator's production packages are the bulk); `vsce ls` shows no `test/`, `scripts/`, `RESEARCH.md` or dev packages.
No file outside `vscode/` and this note changes; the mcp suites are untouched (not rerun beyond one start check).
