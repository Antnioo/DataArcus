# V1 (0.3.1, wave 2): the twin's approval page draws its Arabic pages

Cloud builder, 25 Oct. Branch `feat/0.3.1-twin-preview` from `origin/integration/0.3.1` (fd39bc3, S1 merged). No PR,
no merge (the reviewer reviews and merges). The owner, 25 Oct, after using 0.3.0 on a real report: "in the approval
page I couldn't find the preview sketch". Only the report's plan (create_report / plan_layout) drew its pages; the
approval page of `create_arabic_twin` (the separate twin, and the English-and-Arabic copy `into: "same"`) drew none.

## What the twin already computes (read before planning)
`planTwin` builds the twin in memory (`buildTwin`: every page mirrored, labelled and fitted) and, for the copy,
`languageCopy` (the English pages, the Arabic pages under their new ids, the language buttons, the sync groups) as the
list of files the copy writes. `writeTwin` calls `planTwin` again with the approved plan's data and writes exactly
`P.built` / `P.copy.files`. So plan and write already share one function: nothing has to move, and the preview reads
those same objects. The twin's gate (`Plans.gate`, then `writeTwin`'s checks of labels, terms, options, the source's
print and the model's print) does not read the preview, so it does not change.

## Plan
1. `mcp/lib/arabic-twin.mjs`: one new exported function, `twinPreview(P)`, placed after `twinOutputs` (no line R1
   changes). It turns the plan's own build into the files the shared renderer reads (`Preview.fromFiles`, the function
   the report's preview uses): the separate twin from `P.built.pages` (each page.json and visual.json as the write
   writes them, pages.json in the original's order, the twin's reportExtensions.json and the report's theme); the copy
   from `P.copy.files` (the bytes the write writes; a file copied as it is read from the original). A page hidden in the
   tabs is drawn too (the copy hides one language: the picture shows both); tooltip pages are left out, as on the
   report's page. Each Arabic page is drawn right to left (a page kept left to right because of its picture stays left
   to right); the copy's English pages left to right. The copy's pages come as pairs (English, its Arabic page) by
   `P.copy.pairs`. Colours from the report's theme (background, foreground, first data colour). Types, positions,
   sizes, titles, field names and theme colours only, never a value.
2. `mcp/server.mjs` `create_arabic_twin`: the plan's data gets `preview: twinPreview(P)` (kept with the plan for the
   approval page, never in the answer); the answer gets one sentence: "The approval page shows each Arabic page as it
   will be written" (and, for the copy, beside its English page).
3. `mcp/lib/approval-window.mjs`: `summary('twin')` passes the preview on; `askPage` draws it with the code the report's
   preview uses (Preview.render, Preview.check plus a page's own flags, the same caption with its "to check" words), the
   copy as labelled pairs ("English page 1: name" | "Arabic page 1: name"), side by side, one above the other below
   700 px. The svg keeps `direction="ltr"` (the renderer's T2 fix). One cap for every preview of the approval page,
   `PREVIEW_PAGES_MAX` = 12 (pages; for the copy, pairs): past it, a line says how many are not drawn.
4. Docs: CHANGELOG [Unreleased] line, this file, WORK.md's wave entry.

Not touched: `assets/js/page-preview.js` (no change needed: so no build:min, no ?v= stamps, no website suite beyond a
guard run of the ones that load it), the gate, any other test.

## Decisions I made
1. **No function moved.** The twin's plan already builds what it writes (`planTwin` -> `buildTwin`, `languageCopy`), and
   `writeTwin` writes exactly `P.built` / `P.copy.files` from a fresh `planTwin` with the approved data. The preview reads
   those objects through the renderer's own `fromFiles` (as the report's preview reads the writer's files). The twin's
   gate never reads the preview, so it is unchanged (V1-7).
2. **One cap for every preview on the approval page, `PREVIEW_PAGES_MAX` = 12** (pages; the copy's page pairs). The
   report's preview had no cap (a designed report has 2 pages; hand-placed pages had none): it now has the same one, a
   deliberate change for a hand-placed report of more than 12 pages. 12 chosen, not measured: 12 pairs make 440 KB.
3. **The copy's pairs follow the page's direction**: the approval page of a twin is Arabic (dir="rtl"), so each pair's
   English page is at the right and its Arabic page at the left (reading order: English, then Arabic); stacked under 700 px.
4. **A page hidden in the tabs is drawn** (the copy hides one language's pages: the person approves both); tooltip pages
   are not drawn, as on the report's page.
5. **Colours from the report's theme** (page background, visual background, foreground, first data colour); the
   renderer's defaults where the theme has none.
6. **The renderer is required inside `twinPreview`**, not at the top of arabic-twin.mjs, so the block stays apart from
   the import lines R1 changes; `server.mjs` imports it on its own line for the same reason.
7. The answer's sentence is `approvalPreview` (one field), added in server.mjs after the plan is made: not inside
   `planTwin`'s answer, whose lines R1 changes.
