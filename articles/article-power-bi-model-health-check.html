We Ran a Health Check on Our Own Power BI Model. It Scored 67.

Posted on September 25, 2026

Power BI models rarely break in one day. They grow. A measure is copied to test an idea, a column is imported just in case, a page is duplicated for a meeting. Nobody deletes anything, because nobody knows what is safe to delete. A year later the model is slow to refresh, hard to change and full of things no one can explain.

So we built a free Power BI Model Health Check and ran it first on one of our own production models: a CRM model we built and still maintain. It scored 67 out of 100. Here is what it found, and what each finding means for any model.

The model we checked

24 tables, 245 columns, 410 measures, 37 relationships and a report with 11 pages and 292 visuals. It started small and grew version by version, like most real models. The whole check took under one second, inside the browser.

  • 100 of 245 columns (41%) are not used anywhere: not in a visual, a filter, a measure, a relationship, a sort order or a security rule.
  • 127 of 410 measures (31%) feed no visual, directly or through other measures.
  • 23 fields used in visuals no longer exist in the model. Those visuals show an error.
  • 15 measures use FILTER over a whole table as a CALCULATE filter.
  • Plus smaller things: two calendar tables not marked as date tables, two unused tables, two pairs of identical measures and two USERELATIONSHIP calls that do nothing.

1. Four in ten columns were never used

Every imported column costs memory and refresh time, whether anyone looks at it or not. Text columns with many unique values, like names, notes and IDs, cost the most. In our model the unused ones included customer names, phone numbers, free-text notes and several IDs that were imported "just in case".

The fix is to remove them in Power Query, not to hide them. A hidden column is still loaded and stored. The health check writes the Table.RemoveColumns step for each table for you. One caution: "unused" means unused in this report. If other reports connect to the same model, check those first.

2. Twenty-three visuals pointed at measures that no longer exist

This was the finding we did not expect. When a measure is renamed or deleted, Power BI does not warn you about every visual that used it. The visual simply shows an error the next time someone opens that page. Most of ours were on a test page and a duplicated page that should have been deleted, but a few were on pages people use every week.

The check lists each broken field with the pages it appears on, so the fix takes minutes: open the page and replace or remove the field.

3. FILTER over a whole table

This pattern is everywhere, because it is the first way most of us learned to write a filtered measure:

// Scans every row of the table
Qualified Leads =
CALCULATE ( [Leads], FILTER ( 'Leads Fact', 'Leads Fact'[Status] = "Qualified" ) )

// Filters one column: much faster
Qualified Leads =
CALCULATE ( [Leads], KEEPFILTERS ( 'Leads Fact'[Status] = "Qualified" ) )

FILTER(Table, ...) as a CALCULATE filter builds a table of every column of every row that passes, and applies all of it. A filter on the one column you care about lets the engine work on that column alone. In almost every model the result is the same, and KEEPFILTERS keeps it that way when a slicer is already filtering that column. Without it, the column filter would replace the slicer.

4. Small things that add up

  • Calendar tables not marked as date tables. Marking them makes time intelligence more reliable. It takes ten seconds.
  • USERELATIONSHIP on relationships that are already active. It only does something on inactive relationships. On an active one it just confuses the next person who reads the measure.
  • Identical measures under different names. Sooner or later someone edits one and forgets the other, and two numbers that should match stop matching.
  • Tables nothing uses. Two tables were only used by measures that were themselves unused. The check follows these chains, which is almost impossible to do by hand.

How the check works, and why your file stays with you

The tool reads a Power BI template (.pbit). A template has your model and report layout but no data rows, so it stays small even for very large models. The file is opened inside your browser tab and never uploaded. The tool maps every measure to the columns and measures it depends on, then follows every visual, filter, relationship and security rule to see what is really used.

Check your own model in three steps

  • In Power BI Desktop: File > Export > Power BI template.
  • Drop the .pbit on the Model Health Check.
  • Start with the "Fix these first" list. Then copy the cleanup scripts and download the documentation for your team.

We are cleaning up our own model now, starting with the broken visuals and the unused columns. Our goal is a score above 85. The first check takes one minute, and it will likely surprise you as much as it surprised us.
